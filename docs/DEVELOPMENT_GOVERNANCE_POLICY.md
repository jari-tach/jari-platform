# SAEQ DRIVER — Development Governance Policy
## Permanent Engineering Directive · Version 1.1

> **الحالة:** إلزامي  
> **الإصدار:** 1.1 (الملحق A — Decision Hierarchy and AI Recommendation Policy)  
> **التاريخ:** 2026-07-25  
> **نطاق التطبيق:** جميع أعمال تطوير SAEQ Driver الحالية والمستقبلية  
> **آلية Cursor:** `.cursor/rules/saeq-development-governance.mdc` (`alwaysApply: true`)  
> **التجاوز:** فقط بقرار معماري صريح (ADR مقبول) أو موافقة صريحة من مالك المشروع  

عند التعارض بين المصادر، يُطبَّق الترتيب الرسمي في **§14 Decision Hierarchy**.

---

## الغرض

هذه التوجيهات إلزامية لجميع أعمال تطوير مشروع SAEQ Driver. تطبَّق على جميع المراحل الحالية والمستقبلية.

---

## 1. فلسفة التطوير

يجب أن يكون التطوير: تدريجيًا، صغير النطاق، قابلًا للاختبار، قابلًا للمراجعة، قابلًا للتراجع، موثقًا.

يمنع تنفيذ تغييرات كبيرة غير قابلة للمراجعة.

---

## 2. دورة حياة أي Feature

أي Feature جديدة يجب أن تمر بالترتيب التالي (يمنع تخطي أي خطوة):

1. مراجعة Roadmap.
2. مراجعة Decision Hierarchy.
3. إنشاء Feature Branch مستقل.
4. تنفيذ Feature واحدة فقط.
5. تشغيل اختبارات المرحلة.
6. Runtime Validation إذا كان السلوك التشغيلي قد تغيّر.
7. Quality Gate.
8. Commit واحد فقط.
9. مراجعة واعتماد.
10. الانتقال للمرحلة التالية.

---

## 3. سياسة Git

- يبدأ كل Feature من آخر Commit معتمد.
- Branch مستقل لكل Feature أو Phase.
- يمنع العمل المباشر على الفرع الرئيسي.
- يمنع دمج أكثر من Feature رئيسية في Commit واحد.
- يمنع `git push` قبل اعتماد المرحلة.
- يمنع بدء المرحلة التالية قبل إغلاق الحالية.
- رسائل Commit متوافقة مع Conventional Commits.

---

## 4. التحكم في النطاق

كل مرحلة لها نطاق واضح.

ممنوع: Features خارج النطاق، إصلاحات عشوائية غير مرتبطة، Refactoring واسع، تغيير Architecture دون ADR، إضافة Dependencies دون موافقة، تعديل Customer/Merchant/Admin داخل مستودع Driver.

إذا ظهر تعديل خارج النطاق: **توقف وأبلغ.**

---

## 5. سياسة الاختبارات

أي Feature جديدة يجب أن تضيف أو تحدّث الاختبارات المناسبة (Unit / Widget / Integration / Runtime حسب الحاجة).

لا يجوز تقليل عدد الاختبارات أو إزالة اختبارات دون سبب موثق.

---

## 6. بوابة الجودة

قبل أي Commit يجب أن تنجح فحوص المرحلة المطلوبة، مثل:

- `dart format` (الملفات المعدّلة فقط)
- `git diff --check`
- `flutter analyze`
- `flutter test`
- `flutter build`
- Runtime Validation (إن أثّرت المرحلة على التشغيل)

نجاح البناء وحده غير كافٍ.

---

## 7. Runtime Validation

أي مرحلة تؤثر على Navigation / Authentication / Startup / Lifecycle / State Restoration / Services / Routing / Persistence يجب اختبارها على جهاز Android فعلي قبل اعتمادها.

لا يُستعاض بالمحاكي إلا عند وجود سبب موثق.

---

## 8. الديون التقنية

أي مشكلة تُكتشف خارج نطاق المرحلة: لا تُصلح تلقائيًا، لا تُهمل، تُوثَّق كدين تقني، ويُقترح وقت مناسب لمعالجتها.

---

## 9. التوثيق

كل مرحلة تحدد بوضوح: الهدف، النطاق، الملفات المعدّلة، الاختبارات، النتائج، المخاطر، الديون التقنية، قرار المرحلة.

إذا أثّرت على الخطة العامة: حدّث Roadmap.

---

## 10. الأمان

ممنوع: مفاتيح/Tokens/أسرار حقيقية، كلمات مرور ثابتة، تجاوزات أمنية مؤقتة، Fake implementations تعمل في Production دون Guard.

---

## 11. Definition of Done

لا تُعتبر المرحلة مكتملة إلا إذا:

- تحقق الهدف الوظيفي.
- نجحت جميع الاختبارات المطلوبة.
- نجح Runtime Validation عند الحاجة.
- لم يظهر Regression.
- تم تحديث التوثيق.
- تم إنشاء Commit واحد فقط.
- لم يُنفَّذ `git push`.
- تمت مراجعة المرحلة واعتمادها.

---

## 12. قاعدة الإيقاف الإجباري

توقف واطلب مراجعة قبل المتابعة إذا تطلّب التنفيذ: تغيير Architecture، إضافة Dependency، إعادة كتابة Router، إعادة تصميم State Management، تعديل Database Layer جذريًا، تعديل Security Contracts، Backend Production Integration، حذف ملفات أساسية، تعديل ADR، أو أي عمل خارج النطاق.

لا يُتخذ قرار معماري أثناء التنفيذ دون موافقة.

---

## 13. المبدأ الذهبي

**الجودة أهم من السرعة.**

لا تُغلق أي مرحلة حتى تصبح مستقرة، قابلة للاختبار، موثقة، قابلة للصيانة، وقابلة للتوسع.

الهدف ليس إنهاء أكبر عدد من المراحل، بل بناء منصة مستقرة يمكن الاعتماد عليها لسنوات.

## 14. Decision Hierarchy

عند وجود تعارض بين التعليمات أو الوثائق أو التوصيات، يجب الالتزام بالترتيب التالي من الأعلى إلى الأدنى:

1. Architectural Decision Records (ADR)
2. PROJECT_BIBLE
3. ENTERPRISE_ARCHITECTURE
4. SYSTEM_ARCHITECTURE
5. DEVELOPMENT_GOVERNANCE_POLICY
6. PHASE ROADMAP
7. المرحلة الحالية (Current Phase Instructions)
8. المهمة الحالية (Current Task Instructions)
9. توصيات الذكاء الاصطناعي

لا يجوز تخطي هذا الترتيب.

إذا تعارض مصدران:

- يُعتمد الأعلى في الهرمية.
- يُوثَّق سبب استبعاد الأدنى إذا كان لذلك أثر على التنفيذ.
- لا يُتخذ قرار معماري جديد أثناء التنفيذ دون ADR أو موافقة صريحة.

> ملاحظة: قيود منصة SAEQ (تطبيق Driver فقط، منع دمج الأدوار، إلخ) في
> Master Development Directive تبقى ملزمة لأنها تستند إلى ADR-013 و
> PROJECT_BIBLE — أي إلى مستويات أعلى من هذه السياسة.

---

## 15. AI Recommendation Policy

أي توصية يقدمها الذكاء الاصطناعي (Cursor أو ChatGPT أو أي مساعد آخر) تعتبر اقتراحًا هندسيًا وليست قرارًا ملزمًا.

قبل تنفيذ أي توصية يجب التحقق من توافقها مع:

- Decision Hierarchy.
- Architecture الحالية.
- ADR.
- Roadmap.
- نطاق المرحلة الحالية.
- متطلبات الجودة والأمان.

إذا تعارضت التوصية مع أي عنصر أعلى في الهرمية:

- تُرفض.
- أو تُؤجل.
- أو تُحال إلى ADR جديد.

ولا يجوز تنفيذها مباشرة.

---

## 16. Architectural Change Policy

أي تعديل يؤثر على Architecture يعتبر قرارًا معماريًا.

ومن أمثلته:

- تغيير طبقات المشروع.
- تغيير State Management.
- تغيير Dependency Injection.
- تغيير Routing Strategy.
- تغيير قاعدة البيانات.
- تغيير Security Model.
- تغيير Authentication Flow.
- إضافة خدمة مشتركة تؤثر على جميع Features.

عند ظهور مثل هذا التغيير:

- توقف التنفيذ.
- قيّم الأثر.
- أنشئ ADR إذا لزم.
- لا تتابع التنفيذ قبل اعتماد القرار.

---

## 17. Technical Debt Policy

أي دين تقني يتم اكتشافه أثناء التطوير يجب أن:

1. يُوثَّق.
2. يُصنَّف حسب الخطورة.
3. يُربط بالمرحلة المناسبة لمعالجته.
4. لا يُصلح إذا كان خارج نطاق المرحلة الحالية، إلا إذا كان:
   - يمنع إكمال المرحلة.
   - يسبب خللًا أمنيًا.
   - يؤدي إلى فقدان بيانات.
   - يمنع اجتياز Quality Gate.

---

## 18. Quality Regression Policy

لا يجوز قبول أي مرحلة إذا نتج عنها تراجع في الجودة.

يشمل ذلك:

- انخفاض عدد الاختبارات دون سبب موثق.
- ظهور Flutter Analyze Errors جديدة.
- فشل Build.
- فشل Runtime.
- انخفاض مستوى الأمان.
- تراجع الأداء بصورة ملحوظة.
- كسر Feature مستقرة سابقًا.

أي Regression يجب:

- إصلاحه قبل الإغلاق.
- أو توثيقه واعتماد استثناء صريح.

---

## 19. Documentation Policy

كل مرحلة تطوير يجب أن تنتج وثيقة تقرير رسمية.

ويجب أن تتضمن على الأقل:

- الهدف.
- النطاق.
- الملفات المعدّلة.
- الاختبارات.
- نتائج Runtime.
- المخاطر.
- الديون التقنية.
- Commit Hash.
- قرار المرحلة.
- توصية المرحلة التالية.

لا تعتبر المرحلة مغلقة دون تقريرها الرسمي.

---

## 20. Long-Term Maintainability Principle

جميع القرارات الهندسية يجب أن توازن بين:

- سهولة الصيانة.
- قابلية التوسع.
- الاختبار.
- وضوح الكود.
- الاستقرار طويل المدى.

ولا يجوز التضحية بهذه المبادئ لتحقيق سرعة تنفيذ مؤقتة.

---

## 21. Golden Rule

إذا تعارضت السرعة مع الجودة:

**الجودة هي القرار المعتمد.**

إذا تعارضت سهولة التنفيذ مع صحة Architecture:

**تُحافظ على Architecture.**

إذا تعارض اقتراح مساعد ذكي مع الوثائق الرسمية:

**تُعتمد الوثائق الرسمية.**

الهدف النهائي للمشروع ليس إنهاء أكبر عدد من المراحل، بل بناء منصة مستقرة، آمنة، قابلة للتوسع، وقابلة للصيانة لسنوات طويلة.
