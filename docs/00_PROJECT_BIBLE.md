## 1. رؤية المشروع

مشروع **SAEQ** ليس مجرد تطبيق Flutter واحد.  
بل هو منصة تقنية متكاملة (Enterprise Platform) تخدم المملكة العربية السعودية وتدعم التوسع الإقليمي المستقبلي.

### 1.1 التطبيقات الأربعة

يتكون مشروع SAEQ من أربع منصات رئيسية:

| # | اسم التطبيق | الاسم الإنجليزي | المسؤولية |
|---|-------------|-----------------|-----------|
| 1 | جاري | **Jari** (Customer Application) | طلبات العملاء، التتبع، المدفوعات |
| 2 | فزعة | **Fazaa Driver** (Driver Application) | توصيل الطلبات، التنقل، الأرباح |
| 3 | منفعة | **Manafa Merchant** (Merchant Application) | إدارة القوائم، معالجة الطلبات |
| 4 | لوحة التحكم | **SAEQ Admin Dashboard** | إدارة النظام بالكامل |

> ⚠️ **قرار معماري ملزم:** كل تطبيق من الأربعة أعلاه هو **تطبيق مستقل بالكامل** (مشروع مستقل، Package Name/Bundle ID مستقل، هوية بصرية مستقلة، دورة Build/Test/Release مستقلة، صفحة متجر مستقلة). **يُمنع** دمج أكثر من دور (سائق/عميل/تاجر/إدارة) داخل تطبيق Flutter واحد يعتمد على اختيار نوع المستخدم بعد تسجيل الدخول. التطبيقات الأربعة تتصل ببنية خلفية مشتركة فقط (Backend، API Gateway، المصادقة، قاعدة البيانات المركزية). راجع القرار الكامل في [ADR-013: Separate Applications Strategy](./adr/ADR_SEPARATE_APPLICATIONS_STRATEGY.md). المشروع الحالي `saeq_driver` يمثل تطبيق **SAEQ Driver (فزعة)** فقط، ولا يحتوي على أي شاشات أو منطق خاص بالأدوار الأخرى.

### 1.2 مكوّنات المنصة الكاملة

بالإضافة إلى التطبيقات الأربعة، تشمل المنصة:

- قاعدة بيانات مركزية
- فهرس منتجات مركزي
- سوق الجملة
- سوق التجزئة
- خدمات الذكاء الاصطناعي (مستقبلًا)
- التكامل مع الجهات الحكومية السعودية

### 1.3 المهمة

بناء منصة متكاملة قابلة للتوسع، قابلة للصيانة، آمنة، وعالية الأداء، تخدم المملكة العربية السعودية وتدعم التوسع الإقليمي المستقبلي.

### 1.4 المبادئ الأساسية

كل قرار برمجي يجب أن يعطي الأولوية لـ:

| المبدأ | الوصف |
|--------|-------|
| **قابلية التوسع** | يجب أن يتعامل النظام مع النمو في المستخدمين، الميزات، والحركة دون إعادة تصميم أساسي. |
| **قابلية الصيانة** | يجب أن يكون الكود سهل الفهم، التعديل، والتوسيع من قبل فرق بمستويات خبرة مختلفة. |
| **الأمان** | يجب تأمين جميع البيانات، والاتصالات، وتفاعلات المستخدم من التصميم. |
| **الأداء** | يجب أن يوفر التطبيق تجربة سلسة ومستجيبة في جميع الظروف. |
| **العمارة النظيفة** | يجب أن تتدفق الاعتماديات إلى الداخل؛ يجب أن يكون منطق الأعمال مستقلًا عن الأطر. |
| **معايير برمجة مؤسسية** | ممارسات برمجية موحدة، موثقة، ومفروضة عبر جميع الفرق. |
| **التوسع المستقبلي** | يجب أن تتيح العمارة تطبيقات، خدمات، وتكاملات جديدة دون عناء. |

## 2. أهداف المشروع

### 2.1 الأهداف الإستراتيجية

1. بناء منصة توصيل متكاملة تخدم جميع فئات المستخدمين في المملكة العربية السعودية.
2. إنشاء بنية تقنية قابلة للتوسع لسنوات قادمة، وليس فقط للإصدار الأول.
3. توفير تجربة مستخدم عربية بالكامل (RTL) مع دعم متعدد اللغات.
4. الامتثال لجميع المتطلبات الحكومية السعودية (ZATCA، نظام وصل، منصة بلدي، النفاذ الوطني، العنوان الوطني).
5. دمج خدمات الذكاء الاصطناعي تدريجيًا لتحسين التوصيل والتنبؤ بالطلبات.

### 2.2 الأهداف التقنية

1. اعتماد **Clean Architecture** مع تنظيم **Feature-First**.
2. اتباع مبادئ **SOLID**، **DRY**، **KISS**.
3. دعم التطبيقات الأربعة على الأقل على المنصات التالية: Android، iOS، ومع الوقت Web وDesktop.
4. دعم اللغات: العربية (RTL)، الإنجليزية (LTR)، الهندية، البنغالية.
5. تحقيق تغطية اختبارية تبلغ 80% على الأقل.
6. ضمان الأمان على جميع الطبقات: التخزين، الشبكة، المصادقة، التفويض.

## 4. قواعد المشروع

### 4.1 قواعد البرمجة

| القاعدة | الوصف |
|--------|-------|
| **Clean Architecture** | الاعتماديات تتدفق إلى الداخل؛ منطق الأعمال مستقل عن الأطر. |
| **Feature First** | كل ميزة هي وحدة مستقلة بذاتها. |
| **SOLID Principles** | مبادئ تصميم كائنية التوجه الخمسة. |
| **DRY** | عدم تكرار الشيفرة. |
| **KISS** | احرص على البساطة. |
| **Modular Architecture** | بنية موديولية قابلة لإعادة الاستخدام. |
| **Enterprise Level** | مستوى مؤسسي في جميع الجوانب. |

### 4.2 قواعد التوثيق

| القاعدة | الوصف |
|--------|-------|
| **عدم تكرار المعلومات** | لا يُسمح بوجود نفس الشرح في أكثر من ملف. |
| **روابط داخلية** | استخدام الروابط بين الملفات بدلاً من التكرار. |
| **مسؤولية واحدة** | كل ملف مسؤول عن موضوع واحد فقط. |
| **قرار معماري واحد** | أي قرار معماري يوثق مرة واحدة فقط. |
| **التعديل الأصلي فقط** | أي تعديل مستقبلي يتم في الوثيقة الأصلية فقط. |

### 4.3 قواعد التسمية

| العنصر | اللغة | المثال |
|--------|-------|--------|
| أسماء الملفات | الإنجليزية | `order_service.dart` |
| أسماء المجلدات | الإنجليزية | `features/orders/` |
| أسماء الكلاسات | الإنجليزية | `OrderService` |
| أسماء الدوال | الإنجليزية | `getOrders()` |
| أسماء المتغيرات | الإنجليزية | `orderList` |
| أسماء قواعد البيانات | الإنجليزية | `orders_table` |
| أسماء الـ API | الإنجليزية | `/api/v1/orders` |

### 4.4 قواعد اللغة

- جميع الشرح، التقارير، الملاحظات، ورسائل التنفيذ باللغة **العربية**.
- داخل الكود: اللغة **الإنجليزية** للكتل والمتغيرات والدوال.
- العربية داخل الكود مسموحة فقط للنصوص الظاهرة للمستخدم.

### 4.5 قواعد التصميم

- **Design System موحد** يستخدم في جميع التطبيقات.
- يشمل: الألوان، الخطوط، الأزرار، البطاقات، الحقول، التنبيهات، الرسائل، الأيقونات، الحركة، الوضع الليلي.
- موحد بين: جاري، فزعة، منفعة، لوحة التحكم.

### 4.6 قواعد اللغات

جميع التطبيقات تدعم منذ البداية:
- العربية (RTL)
- الإنجليزية (LTR)
- الهندية
- البنغالية

## 8. ملاحظات دائمة

1. **هذا الملف مرجع رسمي للمشروع.** أي عمل مستقبلي يجب أن يلتزم به بالكامل.
2. **لا تتخذ أي قرار معمارية جديد دون عرضه أولًا للحصول على الموافقة.**
3. **جميع الشرح، التقارير، الملاحظات، ورسائل التنفيذ باللغة العربية.**
4. **أسماء الملفات، المجلدات، الكلاسات، الدوال، المتغيرات، وقواعد البيانات باللغة الإنجليزية.**
5. **العربية داخل الكود مسموحة فقط للنصوص الظاهرة للمستخدم.**
6. **كل ملف مسؤول عن موضوع واحد فقط (Single Responsibility).**
7. **أي قرار معماري يوثق مرة واحدة فقط.**
8. **أي تعديل مستقبلي يجب أن يتم في الوثيقة الأصلية فقط.**

## 9. سياسة مراجعة التوثيق (Documentation Review Policy)

### 9.1 الغرض

تضمن هذه السياسة أن تكون جميع وثائق المشروع دقيقة، محدثة، وقابلة للصيانة على مدى الطول.

### 9.2 تكرار المراجعة

يجب مراجعة جميع وثائق المشروع:

- **كل 6 أشهر** — تلقائيًا، بدءًا من تاريخ إنشاء كل وثيقة.
- **عند أي تغيير معماري كبير** — يجب مراجعة الوثائق المرتبطة فورًا.

### 9.3 من يجب أن يقوم بالمراجعة

- **فريق العمارة** — مراجعة الوثائق التقنية.
- **المطورون** — مراجعة الوثائق المرتبطة بعملهم.
- **مدير المنتج** — مراجعة الوثائق ذات الصلة بالمتطلبات.

### 9.4 قائمة فحص المراجعة

قبل كل مراجعة، يجب التحقق من:

- [ ] لا يوجد تكرار بين الوثائق.
- [ ] جميع الروابط الداخلية صحيحة.
- [ ] جميع الروابط تشير إلى الملفات المرقمة الجديدة.
- [ ] جميع الأقسام مكتملة.
- [ ] يوجد Version، Status، Author، Review Date، Next Review.
- [ ] جميع الجداول متناسقة.
- [ ] لا يوجد محتوى يتعارض مع PROJECT_BIBLE.

> التفاصيل الكاملة موجودة في [29_DOCUMENT_CHECKLIST.md](./29_DOCUMENT_CHECKLIST.md)

### 9.5 تحديث بعد المراجعة

بعد كل مراجعة:

1. قم بتحديث **Last Updated** و **Review Date** و **Next Review** في كل وثيقة.
2. سجل أي تغييرات في [23_CHANGELOG.md](./23_CHANGELOG.md).
3. إذا تم إغلاق أي قيد، حدث [32_KNOWN_LIMITATIONS.md](./32_KNOWN_LIMITATIONS.md).
